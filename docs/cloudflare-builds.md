# نقل البناء والنشر إلى Cloudflare Workers Builds

## الخطوة الوحيدة التي لا أستطيع تنفيذها

ربط المستودع بـ Workers Builds يتم عبر تفويض **GitHub App** من لوحة Cloudflare.
لا توجد واجهة API لذلك — طلب الميزة ما يزال مفتوحًا في
`cloudflare/workers-sdk` تحت عنوان «Feature Request: API support to enable
Workers Builds Git integration». وهذه البيئة أصلًا لا تصل إلى
`dash.cloudflare.com` ولا `api.cloudflare.com` (رفض عند CONNECT خلال ٠٫٢٥ ثانية).

فكل ما في هذا الملف جاهز، ويبقى الضغط على الأزرار.

## الإعدادات المطلوبة في اللوحة

**Workers & Pages → `pixel-cart-cloud` → Settings → Build**

| الحقل | القيمة |
| --- | --- |
| Git repository | `justrandoomis/Bamw` |
| Git branch | `main` |
| Root directory | `/` (الجذر) |
| Build command | `npm run cf:build` |
| Deploy command | `npm run cf:release` |
| Build variables | لا شيء |

### لماذا ليست الأوامر الافتراضية

**أمر النشر ليس `npx wrangler deploy`** — وهو الافتراضي عند Cloudflare.
ذلك الأمر سبق أن فشل على هذا الحساب **بعد أن أخذ كل الترافيك**: يرفع الـ Worker
ويحوّل الترافيك في نداء واحد ثم يوفّق `zone worker routes`، وهو ما لا يملك
التوكن صلاحية قراءته، فردّ
`GET /zones/…/workers/routes → Authentication error [code: 10000]`.
بناء أحمر لنشرة نجحت فعلًا أسوأ من لا شيء: يغري أحدهم بالتراجع عن إصدار سليم.

`npm run cf:release` يفعل ما يفعله `deploy.yml` منذ ذلك الحادث: نصفان في أمرين.
يرفع النسخة، يقرأ معرّفها من مخرجات wrangler نفسها (لا يخمّن «الأحدث»، فذلك
يتسابق مع أي رفع آخر)، ثم يحوّل ١٠٠٪ من الترافيك إليها.

**أمر البناء يشغّل البوابات الأربع نفسها** التي كان `deploy.yml` يشغّلها قبل
wrangler: typecheck، ثم ٣٬٩٥٠ اختبارًا، ثم lint، ثم build — بـ `&&` بينها، فأول
فشل يوقف كل شيء. بدونها يصبح الدفع إلى `main` نشرًا مباشرًا بلا أي حارس، وهذا
تحديدًا «مسار النشر الثاني غير المحروس» الذي وقع فيه هذا المستودع من قبل.

هناك اختبار يقارن أمر البناء بخطوات `deploy.yml` مباشرة
(`scripts/-the-cloudflare-build-runs-the-same-gates.test.mjs`)، فلو أُضيفت بوابة
في أحدهما ونُسيت في الآخر يسقط الاختبار ويسمّي البوابة الناقصة.

## ما يتغيّر في سلوكك

اليوم: النشر يدوي — تختار `mode: release` من Actions.
بعد الربط: **كل دفع إلى `main` ينشر تلقائيًا** بعد نجاح البوابات.

هذا هو المقصود من النقل، لكنه تغيير حقيقي. سير العمل يبقى كما هو — تعمل على
`claude/**` ثم تدمج إلى `main` — والدمج صار هو النشر.

## Secrets

لا شيء ينتقل. أربعة أسماء فقط في كل المستودع:

| الاسم | إلى أين |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | **يبقى في GitHub** — تحتاجه ٥٥ workflow تشغيلية |
| `CLOUDFLARE_ACCOUNT_ID` | **يبقى في GitHub** — للسبب نفسه |
| `CLOUDFLARE_D1_DATABASE_ID` | **يبقى** — معرّف لا سرّ، وبلا قيمة بدون التوكن |
| `CLOUDFLARE_R2_BUCKET_NAME` | **يبقى** — اسم دلو، لا سرّ |

Workers Builds يعمل **داخل الحساب** ويصادق `wrangler` بنفسه، فلا يحتاج التوكن
ولا معرّف الحساب. ولا شيء منها يُضاف إلى Cloudflare.

وأسرار الـ Worker وقت التشغيل (لا وقت البناء) في Cloudflare أصلًا ولا علاقة لها
بهذا النقل.

## ما يبقى في GitHub Actions، ولماذا

| يبقى | السبب |
| --- | --- |
| `ci.yml` | البوابة على كل دفع لكل فرع، قبل الدمج. لا يحتاج أي سرّ. مجاني تمامًا. |
| **migrations** (`deploy.yml` بخيار `migrate`) | الخطوة الوحيدة التي تمسّ بيانات العملاء ولا تُلغى بإعادة التشغيل. بناء يعمل مع كل دفع يجب ألا يكون هو ما يغيّر قاعدة البيانات. |
| **rollback** (`deploy.yml` بخيار `rollback_to`) | تحويل ترافيك إلى نسخة قائمة. ليس بناءً، ولا مكان له في Workers Builds. |
| `verify-deployment.mjs` + `deployment-state.mjs` | تحقق من الخارج بعد النشر. |
| ~٥٣ workflow تشغيلية | استيراد، تسعير، تدقيق، إصلاح، فحوص، `db-console`، `worker-tail`… ليست بناءً، وتقرأ/تكتب الإنتاج عبر REST. Workers Builds لا يستضيفها. |
| `restore-products.yml` | يستخدم `GITHUB_TOKEN` لقراءة artifacts. لا مقابل له في Cloudflare. |

كل هذه على `ubuntu-latest`، **وهي مجانية بلا حدّ** لأن المستودع عام.

## الحدود والتكلفة

Workers Builds على الخطة المدفوعة: **٦٬٠٠٠ دقيقة بناء شهريًا**، ثم ‎$0.005‎
للدقيقة · ٦ عمليات متوازية · **مهلة ٢٠ دقيقة للبناء**.

البوابات الأربع تستغرق ~٢٫٥ دقيقة محليًا، فالبناء الكامل داخل المهلة براحة،
و٦٬٠٠٠ دقيقة تكفي مئات عمليات النشر شهريًا.

ملاحظة صريحة: هذا يحوّل دقائق **مجانية** على GitHub إلى دقائق **محسوبة** على
Cloudflare. لا يُتوقع تجاوز الحصة، لكن قول غير ذلك سيكون تضليلًا.

## الخطة، ولماذا لا أعطّل شيئًا الآن

1. اربط المستودع من اللوحة بالإعدادات أعلاه.
2. ادفع تغييرًا صغيرًا إلى `main` وراقب البناء.
3. تحقق أن الموقع يعمل — `market-roulette-check` و`verify-deployment`.
4. **عندها فقط** نعطّل نصف النشر من `deploy.yml`، مع إبقاء migrations
   و rollback و التحقق.

`deploy.yml` يبقى كما هو حتى تثبت الخطوة ٣. تعطيل طريق النشر الوحيد قبل إثبات
بديله يترك المتجر بلا وسيلة نشر، وهذا كسر للموقع بتعريفه.

## تنبيه: مسار نشر ثالث ما يزال في `package.json`

```
cf:deploy → npm run cf:migrate && npm run check && wrangler deploy
```

يطبّق migrations **ثم** ينشر بـ `wrangler deploy` — الأمر الذي يفشل على هذا
الحساب. هذا هو المسار «غير المحروس» القديم الذي يُكتب على لابتوب. لم ألمسه لأنه
خارج ما طُلب، لكنه لغم: من يشغّله يغيّر قاعدة البيانات ثم يصطدم بخطأ الصلاحيات
بعد أن يكون الترافيك قد تحوّل. أقترح حذفه أو تسميته `cf:deploy:legacy` — قل لي
وأفعل.
